# Промпт 3. Сформировать ТЗ

```text
Ты — системный аналитик и product owner. Сформируй проверяемое техническое задание на MVP для кейса FORMA.

Источники в порядке приоритета:
1. `01_Исходные_документы/07_Ответы_клиента_на_уточнения.md`;
2. остальные файлы из `01_Исходные_документы`;
3. зафиксированные решения из `02_Рабочие_шаблоны/02_Вопросы_и_решения.md`;
4. аналитическая записка.

Если источники противоречат друг другу, используй более приоритетный источник и явно занеси решение в раздел рисков/допущений. Не добавляй функции только потому, что они кажутся полезными.

Целевой MVP: простое локальное адаптивное веб-приложение без сервера, авторизации, CRM и реальных внешних интеграций. Однако проверь это ограничение по источникам, а не принимай его слепо.

ТЗ должно содержать:
1. контекст и бизнес-проблему;
2. цель и измеримые метрики;
3. пользователей и роли;
4. границы In Scope / Out of Scope;
5. основной и альтернативные пользовательские сценарии;
6. функциональные требования с ID `FR-XX`;
7. полный словарь полей, вариантов значений и валидаций;
8. прозрачные бизнес-правила квалификации с ID `BR-XX`;
9. состояния интерфейса и тексты ключевых сообщений;
10. нефункциональные требования;
11. не менее 12 критериев приемки в формате Given / When / Then с ID `AC-XX`;
12. ограничения, допущения, риски и открытые вопросы;
13. план пилотной проверки.

Качество формулировок:
- каждое требование должно быть однозначным и проверяемым;
- избегай слов «удобный», «быстрый», «современный» без критерия;
- для каждого Must-требования должен существовать критерий приемки;
- предварительный статус не должен автоматически отказывать клиенту;
- пограничные или неполные случаи должны безопасно переходить в «Нужно уточнить»;
- в ТЗ явно перечисли то, что не входит в MVP.

Запиши итог в новый файл `ТЗ_MVP.md` в корне проекта. Не начинай разработку. В конце сообщения покажи:
- 5 ключевых решений;
- 5 функций, исключенных из MVP;
- открытые вопросы;
- трассировку `бизнес-цель → требование → критерий приемки`.
```
